# VOWP 0.2.0

**Second public release — one home, many surfaces. Early release.**

VOWP is a local-first supervisor for AI coding agents. v0.2 turns it into one
**home** — a VPS or other always-on Linux machine that owns the truth — and
many **surfaces** that talk to it: an opencode desktop app, a Claude app, a
phone over SSH, `vowp chat`, or an MCP client. The home runs one supervisor for
every project, keeps one append-only log per session, measures capacity,
classifies every file it creates, and still ships work only through guarded,
reversible promotions.

VOWP does not fork or spoof a harness. It uses the official headless/JSON
interfaces, stores no harness credentials, and never reads a harness login. It
is MIT licensed.

> **Status.** 0.2.0 is an early release. The v0.2 command surface is
> implemented and acceptance-tested as described below, but the interfaces may
> still change. Read [Known limitations](#known-limitations) before using it for
> unattended or production-critical work. The features deliberately left out of
> v0.2 are in
> [`docs/roadmap.md`](https://github.com/syver777/vowp/blob/main/docs/roadmap.md).

## Install

### New installation: the setup prompt

The recommended path is the prompt at the top of the
[README](https://github.com/syver777/vowp/blob/main/README.md). Paste this into
Claude Code, opencode or another harness on the computer you want to use as the
control machine:

```text
Set up VOWP 0.2.0 for me. Read
https://raw.githubusercontent.com/syver777/vowp/v0.2.0/docs/setup/agent-setup.md
and follow it exactly. Ask me only what it tells you to ask, show me the full plan once,
and run it after I approve. Never ask me to paste a secret into this chat.
```

The harness reads the setup contract, installs the pinned CLI locally, asks its
five questions once, shows the whole plan without changing the home, and runs
it after one approval. It stops at each human hand-off (sudo, a harness
sign-in, a secret, or an owner answer) and then runs `vowp setup verify`. The
setup commands do the real work, so the result does not depend on which harness
runs the prompt.

### Prebuilt binaries

The release has archives for four targets:

| Platform | Architecture | Archive |
|---|---|---|
| Linux (glibc 2.35 or newer) | x86_64 | `vowp-0.2.0-x86_64-unknown-linux-gnu.tar.gz` |
| Linux (glibc 2.35 or newer) | arm64 | `vowp-0.2.0-aarch64-unknown-linux-gnu.tar.gz` |
| macOS | Intel | `vowp-0.2.0-x86_64-apple-darwin.tar.gz` |
| macOS | Apple silicon | `vowp-0.2.0-aarch64-apple-darwin.tar.gz` |

Each archive contains `vowp`, `LICENSE`, `README.md` and
`THIRD-PARTY-LICENSES.md`. Download the archive for your machine, its `.sha256`
file, and the combined `SHA256SUMS` from the release assets:

```sh
VERSION=0.2.0
TARGET=x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, x86_64-apple-darwin, aarch64-apple-darwin
BASE=https://github.com/syver777/vowp/releases/download/v$VERSION

curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz"
curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz.sha256"
curl -fLO "$BASE/SHA256SUMS"

sha256sum -c "vowp-$VERSION-$TARGET.tar.gz.sha256"   # macOS: shasum -a 256 -c ...
tar -xzf "vowp-$VERSION-$TARGET.tar.gz"
"./vowp-$VERSION-$TARGET/vowp" --version              # must print: vowp 0.2.0
```

The Linux archives are built on Ubuntu 22.04 against glibc 2.35; musl systems
such as Alpine are not supported. The macOS archives are not code-signed or
notarized, so Gatekeeper may ask you to confirm the first run.

From a checkout, `scripts/install.sh` performs the same download, verifies the
`.sha256`, checks the binary's version and installs to `~/.local/bin` (or
`--prefix DIR`) without `sudo`:

```sh
VOWP_VERSION=0.2.0 ./scripts/install.sh --no-service --no-cron
```

### crates.io

The seven crates are published in dependency order. The binary package is
`vowp-cli`; the executable is `vowp`:

```sh
cargo install vowp-cli --version 0.2.0 --locked
vowp --version        # vowp 0.2.0
```

This builds from source and needs Rust 1.85 or newer plus a C compiler/linker
for the bundled SQLite build.

### npm

The npm package downloads the prebuilt binary for the current platform; Rust is
not required:

```sh
npm install -g vowp
vowp --version        # vowp 0.2.0
```

Requires Node.js 18 or newer. Supported platforms are the same four targets as
the prebuilt archives. Windows is not supported and is rejected by the package's
`os` field; musl/Alpine is rejected by the postinstall step with an error that
suggests building from source. Set `VOWP_SKIP_DOWNLOAD=1` to install without
the binary, or `VOWP_RELEASE_BASE_URL` to use a mirror.

### Build from source

```sh
git clone https://github.com/syver777/vowp.git
cd vowp
cargo build --release --locked --workspace
cargo install --path . --locked
vowp --version        # vowp 0.2.0
```

Prerequisites are the Rust stable toolchain selected by
[`rust-toolchain.toml`](https://github.com/syver777/vowp/blob/main/rust-toolchain.toml),
`git`, `tmux`, a C compiler/linker for the bundled SQLite build, and a harness
such as Claude Code or opencode installed and signed in. The
[install guide](https://github.com/syver777/vowp/blob/main/docs/guides/install.md)
covers the details.

## Upgrade from 0.1.0

A v0.1 home has one `~/.vowp/vowp.db`. v0.2 splits it into the global database
plus one database per project under `~/.vowp/projects/<name>/`. Session logs,
capsules and blobs stay where they are.

1. **Stop the supervisor and take a backup.** Do not migrate while a
   supervisor is running.

   ```sh
   vowp down                                  # or: systemctl --user stop vowp
   vowp backup                                # v0.1 backup, under ~/.vowp/backups/
   cp -a ~/.vowp ~/vowp-backup-0.1.0          # a filesystem copy is the belt-and-braces copy
   ```

2. **Install the 0.2.0 binary** over the old one (prebuilt archive,
   `scripts/install.sh --download`, `cargo install`, or npm).

3. **Inspect the migration, then run it.**

   ```sh
   vowp migrate --dry-run
   vowp migrate --yes
   vowp doctor
   ```

   `vowp up` also migrates automatically after a backup; pass `--no-migrate`
   only when you intentionally want the refusal instead. On a healthy v0.1
   home the expected dry run is `from 1 to 2`, one project row per registered
   project, the table counts, and a backup path that does not exist yet.

4. **Start the home and check the fleet.**

   ```sh
   vowp up
   vowp status
   vowp fleet status
   vowp project ls
   ```

The migration:

- refuses while a supervisor is running, on a corrupt database, or when a row
  names a project that does not exist;
- writes `~/.vowp/backups/pre-0.2-<timestamp>.db` first and reports the path;
- stages the new files, copies the global and per-project rows, verifies row
  counts and SQLite integrity, then swaps them in;
- leaves session logs unchanged and is restartable from `migration.json` after
  a crash;
- is forward-only and keyed by `PRAGMA user_version`; a database written by a
  newer binary is refused rather than guessed at.

To roll back, keep the reported pre-migration backup:

```sh
vowp migrate --rollback ~/.vowp/backups/pre-0.2-<timestamp>.db
```

`--rollback` restores the v0.1 database, moves the 0.2 project directory aside
and removes `migration.json`. It also refuses while a supervisor is running.
Reinstall the 0.1.0 binary afterwards if you want to keep running the old
version.

The migration acceptance run used a real v0.1 home with three completed jobs,
four sessions and four runs. The dry run and the migration exited 0; an
independent comparison matched every global and project table (19/19 checks,
including the reserved `_node` project), both project databases passed
`integrity_check` and `foreign_key_check`, and the backup/restore drill matched
the live home. Rollback restored the v0.1 file and the v0.1.0 binary still read
all three jobs. The migration backup was
`~/.vowp/backups/pre-0.2-<timestamp>.db`.

After the upgrade, take a fresh backup outside the home:

```sh
vowp backup --to /mnt/backup/
```

Secrets are never included in a backup. Restore them with
`vowp secret set NAME` after a restore.

## What is in 0.2.0

- **One home, one supervisor.** A global database plus one database per
  project, one node supervisor for every active project with fairness weights
  and round-robin L1–L9 steps, per-project isolation (a broken project parks
  alone), and the `vowp-home`/`vowp-<project>` tmux layout. `vowp project
  add|ls|pause|resume|archive|rm|weight` manages the registry.
- **Migration and backup.** `vowp migrate` with a pre-migration backup,
  per-table row-count checks, rollback and crash recovery; `vowp backup` of the
  global database plus every project database, capsules and the catalog, with
  7 daily and 4 weekly copies, offsite rsync/git targets, optional `age`
  encryption, restore and a restore drill.
- **Fleet read model.** `snapshot.json` (`vowp-snapshot/1`) written every tick
  with the supervisor, project, queue, capacity, limit, inbox, session and
  orchestrator cards; `vowp schema snapshot`; `vowp fleet
  status|queue|inbox|capacity`; project rows in `vowp status` and a board that
  shows every project.
- **Measured capacity.** A Linux sampler for memory, swap, load, CPU quota,
  disk and pressure, with a portable fallback; per-run cgroups or a `/proc`
  tree walk; `run_usage` and pooled p50/p90 estimates. Deterministic admission
  before every worker/verifier/planner/keeper run, a waiting reason on the
  board, brakes that stop admissions and never kill running work, `auto` and
  `fixed` targets, owner override above the advice, and `vowp capacity
  show|report|set`. The keeper-profile advisor proposes; the owner decides.
- **Sessions on every surface.** Surfaces and leases in the global database:
  one writing surface per session, 5-second heartbeats, a 60-second stale
  sweep, takeover with a clear `LeaseRevoked` notice, bounded drain, capsule
  and switch, and read-only follow mode.
- **Remote execution.** `vowp session turn-begin`, `vowp __exec --grant`,
  `vowp session ingest`, a durable per-run spool, idempotent ingest by event id
  and replay after an SSH drop or a killed client. The home stays the only
  writer; the executor owns its harness and injected values.
- **App surfaces and orchestrators.** `vowp chat` as the guaranteed terminal
  surface (`/switch`, `/status`, `/takeover`, `/follow`, `/capsule`). An
  opencode server on the home joined through an SSH tunnel and `opencode
  pair`, and Claude Code Remote Control where a claude.ai login exists; the app
  transcript is mirrored into the canonical log at create/resume/startup.
  `vowp orchestrator new|ls|stop|resume` creates the orchestrator role,
  project-local app config under `~/.vowp/orchestrators/<name>/`, join
  instructions for desktop, phone and chat, and automatic resume after a home
  restart.
- **MCP.** `vowp mcp` is a stdio MCP server with fleet, queue, inbox, capacity
  and session read tools and inbox, job, capacity, tunnel, secret and session
  write tools. Every write checks the lease and records the actor.
- **Control machine.** `vowp control init|status` creates
  `~/.vowp-control/` (no supervisor, loops, graph or worktrees), routes
  project/fleet commands to the home and caches the snapshot with an `as of`
  time. `vowp tunnel open|ls|close` manages `ssh -L` forwards. A phone needs
  only an SSH app and the key and runs the same `vowp chat` on the home.
- **Secrets.** `vowp secret set|ls|rm|upgrade|request`, basic mode and
  vault-user mode through the hidden `vowp __vault-exec`/`__vault-admin`
  helpers; values are never accepted as arguments. Injection by name through
  the harness `env_pass`, exact-value redaction from events, capsules, report
  artifacts, raw run mirrors and the snapshot, and no secrets in backups. A
  one-time `127.0.0.1` paste page with a 10-minute expiry and single use,
  reachable through a tunnel, so a value never enters a chat transcript.
- **Lifecycle and garbage collection.** Lifecycle classes derived from database
  state, `vowp gc` dry run and `--apply` that never touches production, truth,
  open work or secrets, closed-session compaction and run-output
  compression/rotation.
- **AI-first setup.** `vowp setup plan|home|control|verify`: an idempotent,
  fully printed plan; a no-sudo path; a stop at every human hand-off; and a
  fixture verification that merges a job, reads the snapshot from the control
  machine and answers through `vowp chat`.
- **Docs and reference.** The v0.2 specification, concepts for home, capacity,
  data lifecycle and sessions, the setup contract, a phone guide, and a
  regenerated CLI and JSON Schema reference covering the v0.1 and v0.2 command
  surface and every exported type.

The complete feature list is in
[`CHANGELOG.md`](https://github.com/syver777/vowp/blob/main/CHANGELOG.md).

## Acceptance evidence

The v0.2 release is backed by four acceptance records and the repository test
suite. This section summarises the records that gate 0.2.0.

### Fresh setup on a real VM

Both setup halves passed: the Docker rigs (with sudo, without sudo, and with
the user-creation path) and one real Google Cloud Compute Engine VM. The VM
was an Ubuntu 24.04.5 LTS `e2-standard-2` instance in `europe-north1-b`; it
started with no `vowp` binary, no `vowp` user and no `~/.vowp`. The control
machine bootstrapped the pinned 0.2.0 archive, verified its SHA-256, and
installed `vowp 0.2.0`. The final runs of `setup plan`, `setup home --apply
--yes`, `setup control --apply` and `setup verify` all exited 0 on the real
image; the
installed home ran under the real systemd user manager with vault-user secret
mode, wrote the global and project databases, wrote `snapshot.json`, and
answered through `vowp chat`. The no-sudo rig exercised `claude-code` and a
secret hand-off; the sudo rig exercised the user-creation path. The VM and its
boot disk were deleted the same day, and both `gcloud compute instances list`
and `gcloud compute disks list` returned no items.

The tested build needed one accepted workaround: `setup home`'s install phase
failed when the SSH login user's home was not traversable by the target user
(`sh: 22: cd: can't cd to .`, exit 7). The fix for the remote installer's
working directory and `install.sh`'s `SCRIPT_DIR` lookup is in the final tree;
the acceptance run used `chmod 0755` on the test login home to get past it.
The literal README prompt URL and the `v0.2.0` release tag returned 404 during
acceptance because the release was not published yet; the run used the tested
contract file and a loopback release mirror instead. A post-release re-run must
fetch the real tag and pass the real checksum.

**Real opencode and Claude Code harness check: Not run.** The Docker and VM
runs used fake version-answering harness binaries and login markers because the
repository rules forbid real harness processes, model turns and credentials in
tests. The two harness identities were exercised as distinct setup answers and
profiles. A release-time owner check should paste the README prompt into a real
opencode and a real Claude Code on a clean control machine.

### Surfaces and SSH drop

The automated scope passed on every path this build can drive:

- the real opencode desktop web UI and the real `opencode mini` terminal UI
  shared one live native session and saw each other's turns;
- an app→`vowp chat` lease move wrote the capsule, the new turn started with
  `note: handoff`, and the old app's `vowp mcp` write was refused with
  `Taken over by … This surface is now read-only (follow mode).` — measured at
  82 ms, well inside the 2-second bound;
- a chat fallback drained a mid-flight turn, wrote the capsule and ended the
  old turn `interrupted` with contiguous sequence numbers;
- a combined app/lease move mid-turn produced the same refusal, a capsule, an
  old `__exec` exit 75 and a new turn from the capsule;
- the SSH-drop test killed the laptop executor's SSH child after three spooled
  events. The executor reconnected and replayed from the first unacknowledged
  frame: the home log had 19 contiguous events, 12 unique assistant lines and
  exactly one copy of every event; the spool had 13 events (12 plus the
  summary) and all 12 were acknowledged.

The surfaces work also fixed an explicit `--project <name>` failure outside the
checkout when the project config had no `project.path`; the final tree defaults
it from the directory containing `vowp.toml`.

The owner-device checks below were **not run**. They need the owner's Mac and
phone and are recorded in full in the surfaces acceptance record. The owner should
use the final build.

1. **opencode desktop app on the Mac — Not run.**
2. **The same live session on the phone over SSH — Not run.**
3. **A real-app move to another app mid-turn — Not run.**
4. **Claude Remote Control — Not run.** The test home had no claude.ai login;
   the honest refusal path (`orchestrator new --app claude-code` exits 5 with
   the login message) was verified instead.

### Dogfood orchestrator

The automatable rehearsal **passed**. On a temporary VOWP home, the run
created a real `opencode` orchestrator, printed its desktop/phone/chat join
instructions, seeded the session from an orchestrator handoff, saved status and
a `vowp session capsule`, and confirmed the seed through `vowp chat`. The same
session's `vowp mcp` server read the fleet and added a release job with the
session/surface recorded as the actor; the home supervisor ran the job through
its gates and the merge queue, and the same session then reported the live
release view (two done jobs, the last merge commit and branch). `orchestrator
stop` and `resume` kept the same VOWP session id and refreshed the app join
block.

The real app host was opencode 2.0.28, but the turn executor was a
deterministic CLI stand-in that read the real fleet; no real model turn or
provider call was made. The rehearsal found one product gap — a project-bound
orchestrator's own directory was outside the project's cwd allow-list — and the
final tree fixes it (`crates/vowp-core/src/session` shares one `check_cwd` and
allows `<VOWP_HOME>/orchestrators`). A pre-fix build needs the documented
`cwd_allow` workaround.

**The live move on the production home and the owner's laptop/phone joins were
NOT RUN.** The owner-device scope decision defers these to the owner; they are
not waived. The exact commands, expected results and "Not run" markers are in
the dogfood acceptance record. The five owner steps are:

1. **Move the current orchestrator into the live VOWP home — Not run.**
2. **opencode desktop app on the Mac — Not run.**
3. **The same live session on the phone over SSH — Not run.**
4. **The chat fallback on the same session — Not run.**
5. **Continue the release from the session — Not run.**

## Known limitations

These are the limits that matter for a first v0.2 user. They are taken from the
current code, the acceptance records and the user documentation.

### Product shape

- **One home.** There is no replication, leader election or multi-home
  scheduler. A second home is a separate installation.
- **No public HTTP or SSE API.** The planned daemon API, web window and phone
  browser board are v0.3 design notes. v0.2 has no listening public port; app
  hosts and the secret page are loopback-only and reached through SSH.
- **SSH is the transport.** A control machine needs key-based, batch-mode SSH
  to the home. A phone needs an SSH app and the key.
- **Apps keep their own limits.** VOWP can configure and host an app; it cannot
  close another vendor's window or force an app build to expose MCP tools.
  opencode 2.0.28 can report the server `connected` without exposing its tools
  to the model; `vowp chat` is the tool-free fallback.
- **One operator.** Multi-user accounts, quotas, roles and audit are not in
  v0.2.
- **Linux home, Linux/macOS control.** Windows is not supported and there is no
  native VOWP desktop app; the apps are the surfaces. The macOS and aarch64
  release targets are built and smoke-tested by the release workflow on native
  runners, not by the local preparation run.
- **No continuous app-transcript watcher.** The mirror runs at orchestrator
  create/resume/startup; between those calls the app owns its transcript.

### Secrets

- **Secret redaction has known gaps.** The migration, GC and secrets acceptance
  run's redaction test failed in two
  production paths: a jobless planner/keeper run's raw mirror is not redacted
  (`vault::redact_job_artifacts` returns early when there is no job id), and
  `runs.detail` stores the last assistant text through the shape-based
  classifier rather than the vault exact-value redactor. Exact-value redaction
  also does not cover the supervisor log, gate command evidence, ledger rows,
  the switch turn path or the `session watch` importer. Treat every harness as
  able to persist what it prints; the secret-scan gate is a backstop, not a
  guarantee.
- **Injection reaches harness `env_pass` only.** Promotion/deploy commands run
  with an empty environment in this build; they cannot name secrets yet.
- **Basic mode does not separate the value from the agent's user.** Vault-user
  mode keeps the files out of the runtime user's direct readable tree, but the
  helper that reads them is a broad trust boundary. Neither mode encrypts the
  store at rest. A secret pasted into a chat is already in the model provider's
  transcript — rotate it and use the hidden prompt or the one-time page.
- Secrets are never included in a backup. Restore them by name after a restore.

### Setup and control machine

- **Control-machine fleet commands can exit 127.** `vowp fleet status`,
  `fleet queue` and `fleet inbox` route to a bare `vowp` on the home; a
  non-login SSH `PATH` does not include `~/.local/bin`. `vowp fleet status
  --cached` still works, and `setup home`, `setup control` and `setup verify`
  use the absolute path. Install `vowp` on the remote `PATH` or use the cached
  form until the routing fix lands.
- **First `setup home` on a fresh VM can warn about the user systemd bus.**
  Linger is enabled after the first `systemctl --user` commands, so
  `service.enabled` warns; the idempotent re-run starts the unit and reports it
  `ok`.
- **The read-only setup plan can report a false harness-login hand-off** when
  the login user's home is mode 0750. The apply checks as the target user and
  passes; the plan is cosmetic here.
- **The literal README prompt needs the published tag.** It returned 404
  before 0.2.0 was published. A post-release run must fetch the real tag and
  verify the real checksum.

### Sessions, chat and capacity

- **`vowp chat` seeding is line-oriented.** Each line of stdin is one prompt.
  A multi-line handoff pasted as-is becomes one turn per line; flatten it to one
  line (`tr '\n' ' '`) or wait for a future prompt-file/import command.
- **`session watch` is not incremental and has no `--follow`.** Each pass can
  create a new VOWP session for the same Claude uuid; the importer is for
  one-shot imports in this build.
- **Interval schedules align to the Unix epoch**, not their creation time.
  Time zones are UTC or a fixed offset only.
- **A capacity brake can hold work on a loaded host.** That is the designed
  behaviour; the orchestrator should report the brake and ask the owner before
  overriding it. A brake never kills a running job.
- **The review gate was not re-run end to end in the dogfood rehearsal.** It waited
  on a real swap-growth brake and the rehearsal cancelled that job; the gate's
  coverage is its unit tests. On a busy home, report the brake and ask.

### Owner acceptance still pending

The owner-device click-throughs in the fresh-setup, surfaces and dogfood runs are **not run**, as recorded
above: the real harness prompt, the Mac desktop app, the phone over SSH, the
real-app mid-turn move, Claude Remote Control, the live orchestrator move and
continuing the release from that session. They are not waived and no release
claim replaces them.

## Verification

The release commit is checked with:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
cargo check --workspace --locked
bash docs/tests/run.sh
bash scripts/tests/run.sh
scripts/release/check-packages.sh
scripts/release/publish-crates.sh
```

The archives are built by `.github/workflows/release.yml` on native runners for
the four targets, with `--locked`, a `vowp --version` smoke test, the
third-party licence check, `package-archive.sh`, per-archive `.sha256` files and
the combined `SHA256SUMS`. The workflow creates a **draft** release; the
orchestrator verifies every asset and publishes it after the owner's review.

The test suite is hermetic: temporary homes and repositories, private tmux
sockets and `TMUX_TMPDIR`s, fake harnesses, and no network. The shipped
end-to-end example,
[`examples/hello-vowp`](https://github.com/syver777/vowp/blob/main/examples/hello-vowp/README.md),
runs a three-job graph against fake adapters and passes.
