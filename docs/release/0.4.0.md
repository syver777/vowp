# VOWP 0.4.0

**Fourth public release — local agent nodes, paired surfaces, opt-in offload and hardening. Early
release.**

VOWP is a VPS framework for AI agents to work on projects. v0.4 keeps the v0.3 shape — one **home**
on a Linux VPS that owns the global database, the project databases, every session log and the
supervisor, with many **surfaces** that talk to it — and adds the machine where the work actually
lives. A Mac or Linux machine can join as an outbound **agent node**, pair a local `vowp chat` or
opencode surface, and run an offloaded job while the home stays the only writer. The release also
completes the phase-4 hardening work: optional WSS ingress, a launchd/systemd-user agent service,
surface token rotation, verified git bundle results, separate-user checks, 30-day capacity history,
and a live supervisor drain/upgrade. ASIF 0.4 session export/import is included as a review draft.

VOWP does not fork or spoof a harness. It uses the official headless/JSON interfaces, stores no
harness credentials, and never reads a harness login. It is MIT licensed.

> **Status.** 0.4.0 is an early release. The v0.4 command surface is implemented and tested as
> described below, but the interfaces may still change. Read
> [Known limitations](#known-limitations) before using agent nodes, offload or the ASIF interchange
> for unattended or production-critical work. The features deliberately left out of v0.4 are in
> [`docs/roadmap.md`](https://github.com/syver777/vowp/blob/main/docs/roadmap.md).

## Install

### Prebuilt binaries

The release has archives for four targets:

| Platform | Architecture | Archive |
|---|---|---|
| Linux (glibc 2.35 or newer) | x86_64 | `vowp-0.4.0-x86_64-unknown-linux-gnu.tar.gz` |
| Linux (glibc 2.35 or newer) | arm64 | `vowp-0.4.0-aarch64-unknown-linux-gnu.tar.gz` |
| macOS | Intel | `vowp-0.4.0-x86_64-apple-darwin.tar.gz` |
| macOS | Apple silicon | `vowp-0.4.0-aarch64-apple-darwin.tar.gz` |

Each archive contains `vowp`, `LICENSE`, `README.md` and `THIRD-PARTY-LICENSES.md`. Download the
archive for your machine, its `.sha256` file, and the combined `SHA256SUMS` from the release assets:

```sh
VERSION=0.4.0
TARGET=x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, x86_64-apple-darwin, aarch64-apple-darwin
BASE=https://github.com/syver777/vowp/releases/download/v$VERSION

curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz"
curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz.sha256"
curl -fLO "$BASE/SHA256SUMS"

sha256sum -c "vowp-$VERSION-$TARGET.tar.gz.sha256"   # macOS: shasum -a 256 -c ...
tar -xzf "vowp-$VERSION-$TARGET.tar.gz"
"./vowp-$VERSION-$TARGET/vowp" --version              # must print: vowp 0.4.0
```

The Linux archives are built on Ubuntu 22.04 against glibc 2.35; musl systems such as Alpine are
not supported. The macOS archives are not code-signed or notarized, so Gatekeeper may ask you to
confirm the first run.

The archive contains the `vowp` binary used on the home, control machine and agent node. The same
binary includes the `vowp agent` command and the hidden `vowp agent gateway` listener the home
starts for WSS. `vowp-agent` is also a library crate; there is no separate `vowp-agent` executable
to install.

From a checkout, `scripts/install.sh` performs the same download, verifies the `.sha256`, checks the
binary's version and installs to `~/.local/bin` (or `--prefix DIR`) without `sudo`:

```sh
VOWP_VERSION=0.4.0 ./scripts/install.sh --no-service --no-cron
```

### The daemon and the web window

The browser window is served by the separate `vowp-daemon` binary. The archives above contain
`vowp` only; install the matching daemon as well when you want the window:

```sh
cargo install vowp-daemon --version 0.4.0 --locked
vowp-daemon --help
```

`vowp up` looks for `vowp-daemon` next to the running `vowp` executable, then on `PATH`;
`VOWP_DAEMON_BIN` overrides the lookup. A missing daemon is not fatal: the supervisor prints a
warning and keeps running without the window.

The daemon binds `127.0.0.1` on the home. Reach it from a laptop or phone through the existing
managed SSH tunnel, which `vowp up` prints for the port it actually chose:

```text
web window: http://127.0.0.1:54321/
remote window: vowp tunnel open window --remote-port 54321
  local URL: http://127.0.0.1:<local-port>/ (the command prints the chosen port)
```

### crates.io

The binary packages are `vowp-cli` (the `vowp` executable) and `vowp-daemon` (the loopback API),
installed from crates.io in the usual dependency order:

```sh
cargo install vowp-cli --version 0.4.0 --locked
cargo install vowp-daemon --version 0.4.0 --locked
vowp --version        # vowp 0.4.0
```

This builds from source and needs Rust 1.85 or newer plus a C compiler/linker for the bundled
SQLite build. ASIF 0.4 is a review draft and its adapter is the published `vowp-asif = "=0.1.1"`
crate from crates.io; see [ASIF interchange](#asif-interchange). The prebuilt archives do not
depend on the crates.io path.

### npm

The npm package downloads the prebuilt `vowp` binary for the current platform; Rust is not required:

```sh
npm install -g vowp
vowp --version        # vowp 0.4.0
```

Requires Node.js 18 or newer. Supported platforms are the same four targets as the prebuilt
archives. Windows is not supported and is rejected by the package's `os` field; musl/Alpine is
rejected by the postinstall step with an error that suggests building from source. Set
`VOWP_SKIP_DOWNLOAD=1` to install without the binary, or `VOWP_RELEASE_BASE_URL` to use a mirror.
The npm package installs `vowp` only; install `vowp-daemon` separately for the web window.

### Build from source

```sh
git clone https://github.com/syver777/vowp.git
cd vowp
cargo build --release --locked --workspace
cargo install --path . --locked
cargo install --path crates/vowp-daemon --locked
vowp --version        # vowp 0.4.0
```

Prerequisites are the Rust stable toolchain selected by
[`rust-toolchain.toml`](https://github.com/syver777/vowp/blob/main/rust-toolchain.toml), `git`,
`tmux`, a C compiler/linker for the bundled SQLite build, and a harness such as Claude Code or
opencode installed and signed in. The
[install guide](https://github.com/syver777/vowp/blob/main/docs/guides/install.md) covers the
details, including adding an agent node.

## Upgrade from 0.3.0

0.4.0 moves the global database to schema 7 and each project database to schema 2. A home created
by the 0.3.0 release is schema 2/1; opening it with the new binary applies the intervening
migrations in order. The final global v6 → v7 step writes `backups/pre-0.7-<milliseconds>.db`
before it changes the file; the project v1 → v2 step writes
`backups/project-<name>-pre-0.6-<milliseconds>.db`; earlier pending steps write their own backup.
A live supervisor defers an automatic migration for normal reads, so use the drain path when you
want to upgrade in one move.

1. **Stop the supervisor and take a backup.**

   ```sh
   vowp down                                  # or: systemctl --user stop vowp
   vowp backup                                # under ~/.vowp/backups/
   cp -a ~/.vowp ~/vowp-backup-0.3.0          # a filesystem copy is the belt-and-braces copy
   ```

2. **Install the 0.4.0 binary and daemon** over the old ones (prebuilt archive,
   `scripts/install.sh`, `cargo install`, or npm for `vowp` and `cargo install vowp-daemon` for the
   window).

3. **Check the home, then start it.**

   ```sh
   vowp doctor
   vowp up
   vowp status
   vowp fleet status
   vowp capacity history --since 1d --bucket 1h
   ```

   `vowp up` starts the daemon when it finds it and starts the loopback WSS listener only when
   `[ingress.wss].enabled = true`. It prints the window URL and tunnel hint, and keeps the
   supervisor running if the daemon is missing.

4. **Use the live upgrade path for a running home.** `vowp down --drain` stops admitting new work
   and lets active runs and gate tasks finish before the supervisor exits. `vowp up --replace`
   drains the old supervisor, applies any pending schema migration with no active children, and
   starts the current binary. Neither command kills a running run.

   ```sh
   vowp up --replace
   ```

5. **Update agent nodes.** Install the same 0.4.0 binary on each Mac or Linux agent node and check
   the connection:

   ```sh
   vowp agent status
   vowp agent doctor
   ```

   A paired surface keeps its token unless it expired or was revoked. Restart or reinstall the
   service only if the node runs under `agent service`. A changed system-mode WSS certificate
   fingerprint is still a refusal until the owner verifies it and runs
   `vowp agent trust --fingerprint sha256:<64-lowercase-hex>`.

6. **Roll back on the copy, not the live home.** A 0.3.0 binary refuses a schema-7 file
   (`database schema version 7 is newer than supported 2`). To roll back, stop the supervisor,
   restore the pre-upgrade filesystem copy or a `vowp backup --restore` copy into a staging
   directory, verify it, and start the 0.3.0 binaries against that copy. The full drill, including
   the v6 restore and the upgrade to v7, is in
   [`docs/releases/v0.4-hardening.md`](https://github.com/syver777/vowp/blob/main/docs/releases/v0.4-hardening.md).

Keep the 0.3.0 filesystem copy until you are satisfied with the upgrade. The automatic migration
backups are a second line of defence, not a substitute for your own copy.

## What is in 0.4.0

- **Outbound agent nodes.** `vowp node enroll <name>` on the home creates a pending node and a
  one-time code; `vowp agent enroll` on a Mac or Linux machine redeems it and writes a private node
  key. The node dials the home over SSH stdio by default and proves its Ed25519 identity in the
  `AgentHello` → `HomeChallenge` → `AgentAuth` → `HomeWelcome` handshake. `vowp agent paths
  add|rm|ls` maintains the local project map without re-enrolling.
- **Optional WSS ingress.** `[ingress.wss]` starts a loopback-only WebSocket listener behind an
  owner-operated TLS reverse proxy. The path is exactly `/agent/v1`, the subprotocol is
  `vowp-agent/1`, compression is not offered, and a non-loopback bind is refused. The framed
  protocol, node-key challenge and lease rules are the same as SSH. A changed system-mode leaf
  fingerprint requires the local owner command `vowp agent trust`; a pinned certificate stays a
  hard pin. There is no fallback between transports and no hosted relay.
- **Local `vowp chat` surfaces.** A chat surface pairs over the agent connection, acquires and
  heartbeats the same session lease as the home, ingests turns into the one session log, replays
  its spool after a disconnect, and uses the same lease handoff, takeover and read-only follow
  rules as the home.
- **Local opencode orchestrator surfaces.** The agent hosts a paired opencode orchestrator with a
  mode-0600 agent socket, an opencode SSE bridge and a stdio MCP proxy. Attach/detach, native
  events, turns and MCP calls travel over the one outbound connection under the session lease; the
  home materializes and owns the orchestrator record, the lease handoff and the lifecycle. The MCP
  proxy has a bounded, read-only offline cache with an `as of` line; writes never use it.
- **Opt-in offload.** `[offload]` is off by default. When a project opts in, placement policy, the
  path map, an isolated worktree per job, ordered run events and home verification of the result
  decide what runs where. A push result still needs the node's git credentials. A
  `result_transport = "bundle"` result returns one verified `base..head` git bundle over the
  authenticated agent channel instead: the home checks the size and SHA-256, runs
  `git bundle verify`, accepts exactly one job ref with the base as a prerequisite, and imports it
  into private staging before the `owns_respected` and `secret_scan` gates. Neither transport falls
  back to the other.
- **Private-checkout safety.** A project checkout, worktree root or resolved git directory owned by
  another uid, or group- or world-writable, is refused before a worktree or branch is created.
  Group and world read/execute remain supported. The checks run when the path map is built and
  again at run start.
- **Surface rotation UX.** `vowp surface rotate` mints a fresh 30-day token and shortens the old
  tokens to a ten-minute overlap. `--wait` polls the delivery deadline and exits 7 with
  `rotation_pending` for an offline node; `--grace` extends the overlap up to a 24-hour cap. The
  durable envelope carries `queued_at`/`overlap_until`; `surface ls` shows `PREFIX` and `OVERLAP`,
  and a lost surface is replaced in one transaction with `surface pair --replace`. Rotation and
  revocation write one ledger note without a token or hash.
- **Agent service and separate user.** `vowp agent service install|uninstall|status` writes or
  removes exactly one 0600 launchd `LaunchAgent` or systemd user unit for the current user. The
  unit carries no token, code, key or project path. `agent run --service` writes the launchd
  restart marker and drains the spool and leases on SIGTERM. A dedicated standard account is a
  supported shape: one node name and key per account, owner files protected, and root, foreign or
  loose state directories refused. The separate user is a filesystem boundary, not a sandbox.
- **Capacity history.** Global schema v7 adds `capacity_rollups`. The home aggregates the previous
  completed five-minute bucket on each tick, keeps raw samples for 48 hours and rollups for 30
  days, and never turns a gap into a zero. `vowp capacity history [--since] [--bucket 5m|1h|1d]`
  reads it read-only; `--json` emits `CapacityHistory`. Cost stays in `vowp cost --by day` and is
  not duplicated here.
- **Live supervisor drain and upgrade.** `vowp down --drain` stops admissions while letting active
  runs, gates and merges finish; `vowp up --replace` drains the old supervisor, migrates with no
  active children and starts the new binary. A migration is deferred while another live supervisor
  holds the lock, so ordinary CLI reads work after a binary install.
- **ASIF 0.4 session export/import (review draft).** `vowp session export <id> --format asif`
  writes a deterministic `.asif.zip` through the published `vowp-asif 0.1.1` adapter from
  crates.io, and `vowp session import <file> --format asif` creates one new idle session from a
  package, a standalone `session.json`, a directory or stdin. Export redacts host paths by
  default and accepts repeatable `--redact` literals; import reports declared losses and
  supports `--strict` and `--allow-loss`. The daemon serves a token-free download route, a loss
  preview and a token-gated upload page. ASIF 0.4 is a review draft: the slice does not claim
  ASIF conformance, an exact or lossless round trip, portable continuation or native-harness
  import. The adapter is `vowp-asif = "=0.1.1"` from crates.io, recorded in
  [`docs/design/v0.4/asif-integration.md`](https://github.com/syver777/vowp/blob/main/docs/design/v0.4/asif-integration.md) §4.3;
  `scripts/release/check-packages.sh` passes for all nine workspace crates.
- **Also in 0.4.0.** `vowp session push` streams one session bundle to another node; the daemon has
  token-gated job retry, park and cancel actions plus a read-only `/jobs/{id}` detail page;
  supervisor-log, switch-turn and `session watch` payloads are redacted; and the default fix loop
  is two rounds.

The complete feature list is in
[`CHANGELOG.md`](https://github.com/syver777/vowp/blob/main/CHANGELOG.md).

## Known limitations

These are the limits that matter for a first v0.4 user. They are taken from the current code and the
tests.

### Agent nodes and transports

- **One smoke test, not a soak.** The owner ran the live Mac smoke test once on 2026-11-18. There
  is no multi-day run or daily checklist, and the Mac path has not been proved on every OS
  version.
- **SSH stdio is the default.** The agent dials the home; the home never dials the agent. A
  control machine still needs key-based, batch-mode SSH. WSS needs an owner-operated TLS reverse
  proxy, DNS, a certificate and proxy hardening; VOWP binds loopback only and runs no ACME.
- **The WSS proxy is trusted.** It terminates TLS and can read decrypted frames, including surface
  and lease tokens, prompts and tool output. A compromised proxy is a home compromise: rotate the
  affected surface tokens and revoke the node. Keep its access logs free of frame bodies.
- **No transport fallback.** A WSS agent whose proxy is down reconnects with backoff and spools; it
  does not dial SSH behind the configuration's back. A changed system-mode fingerprint is a
  refusal until the owner runs `vowp agent trust`; a pinned certificate needs re-enrollment.
- **Mac and Linux nodes only.** A dedicated standard account is one node name and one key per
  account. The separate user protects the owner's files, not the agent's own key or tokens from a
  harness running as that user. A macOS `LaunchAgent` needs a GUI login after a reboot; a
  system-wide daemon or root unit is unsupported.
- **Node state is local.** The home sees a node name, public key, path map and capacity; the node
  keeps its own harness login, provider environment and worktrees. VOWP never copies a login or a
  provider key to a node.

### Local surfaces and offload

- **Offload is opt-in.** `[offload]` is off by default, and a project must opt in. A node is
  eligible only when the project is mapped, the base commit is fetchable and the path map is valid.
  A run that cannot be placed stays on the home.
- **Offload returns committed work only.** A push result fetches the pushed `job/<id>` branch; a
  bundle result creates exactly one `refs/heads/job/<id>` with the base as a prerequisite. A dirty
  worktree returns only committed objects, and a run with `base == head` fails `result_empty`.
- **Bundle limits.** The transfer is capped at 256 MiB per bundle, five minutes and 256 KiB of raw
  data per chunk. A disconnect resumes at the acknowledged offset. A transfer or file failure is
  `bundle_failed`; a well-formed but wrong result is `bundle_rejected`; neither leaves a project
  ref, a merge or a staging file after settle.
- **Home-only secrets stay home.** A project that needs a home-only secret is not offloaded. The
  home remains the only writer of the session log and the only merge queue.
- **Local surfaces depend on the app.** The opencode surface needs a local opencode installation.
  The MCP proxy's offline cache is read-only and bounded; writes never use it, and a revoked
  surface clears its entries.

### Rotation and service

- **A queued rotation can be delivered expired.** If the replacement token expires before the node
  reconnects, the gateway still delivers it; the home refuses the expired token on first use and
  the surface must be re-paired. `--wait` stops at its deadline with `rotation_pending`; `--grace`
  is capped at 24 hours. The replacement token still expires after 30 days.
- **The service unit carries no secret.** It contains the binary, arguments, `VOWP_AGENT_HOME`,
  `PATH` and fixed service settings. It does not carry a token, code, key or project path.
  `uninstall` removes only a VOWP-generated unit.
- **The separate user is not a sandbox.** The harness runs as the agent user and can read that
  user's node key and surface tokens if it tries. The boundary protects the owner's files. Group-
  or world-writable checkouts, worktree roots and git directories are refused; group and world
  read/execute remain supported.

### Capacity and live upgrade

- **History is bounded and read-only.** Raw samples are kept 48 hours and five-minute rollups 30
  days. A gap is a gap, not a zero; a fallback sample is labelled `fallback` and its memory/load
  values are not a measurement. `--since` before the retained window is clamped and the command
  says so.
- **No alerts or exports.** There are no capacity alerts, per-node history, Prometheus/OpenTelemetry
  export, configurable retention, cost budgets or chart UI. Cost remains `vowp cost --by day`.
- **A v7 file is not readable by 0.3.0.** The previous binary refuses it rather than downgrading.
  Roll back on the restored copy, never on the live home, and keep your own filesystem backup.
- **The live path waits for work.** `down --drain` and `up --replace` let active runs and gate
  tasks finish and admit no new work while they wait. A long run extends the drain; no active
  child is killed.

### ASIF interchange

- **Review draft only.** ASIF 0.4 export/import reports declared losses and does not claim ASIF
  conformance, an exact or lossless round trip, portable continuation or native-harness import.
  Jobs, gates, leases and project rows are not in the package.
- **The adapter is a crates.io dependency.** `vowp-asif = "=0.1.1"` resolves from crates.io in
  `Cargo.lock`; the source is recorded in
  [`docs/design/v0.4/asif-integration.md`](https://github.com/syver777/vowp/blob/main/docs/design/v0.4/asif-integration.md) §4.3.
  `scripts/release/check-packages.sh` packages and dry-run publishes all nine workspace crates
  cleanly.
- **Remote export and import are narrow.** Export verifies the hidden stream's byte count and
  SHA-256 before writing the local package; `--report` and directory input are refused with
  `--node`. Import never overwrites, merges or keeps the source id.

### Platform and product shape

- **One operator, one home.** There is no replication, leader election or multi-home scheduler,
  and no multi-user accounts, quotas, roles or audit beyond the existing ledger. A second home is
  a separate installation.
- **Linux home, Linux/macOS control and agent nodes.** Windows is not supported and there is no
  native VOWP desktop app; the apps are the surfaces. The home opens no public port by default.
- **No hosted relay.** SSH, or the owner's WSS proxy, is the remote path. There is no relay that
  removes the SSH key or the proxy from the trust story.
- **Secret redaction still has known gaps.** Redaction is exact-value only. Gate command evidence,
  ledger rows and the report/run mirror during a turn stay raw, and a secret added after the
  supervisor starts is picked up only at its next restart. Treat every harness as able to persist
  what it prints; the secret-scan gate is a backstop, not a guarantee.

`TMUX_TMPDIR`s, fake harnesses and service managers, and no network. The shipped end-to-end
example,
[`examples/hello-vowp`](https://github.com/syver777/vowp/blob/main/examples/hello-vowp/README.md),
runs a three-job graph against fake adapters and passes.
