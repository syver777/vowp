# VOWP 0.1.0

**First public release — early release.**

VOWP is a local-first supervisor for AI coding agents. It runs the harnesses you
already use — Claude Code, opencode or a generic CLI — as a small team of job
workers on your own machines. Work is a job graph; deterministic loops keep it
moving; every job runs in a tmux window you can watch; sessions keep their
context in an append-only event log and can move between harnesses, models and
nodes; and finished work reaches production only through guarded, reversible
promotions.

VOWP does not fork or spoof a harness. It uses the official headless/JSON
interfaces, stores no credentials and never reads a harness login. It is MIT
licensed.

> **Status.** 0.1.0 is the first public release and the v0.1 command surface is
> implemented, but this is young software. Read [Known limitations](#known-limitations)
> before using it for unattended or production-critical work. The scope that is
> deliberately not in v0.1 is in
> [`docs/roadmap.md`](https://github.com/syver777/vowp/blob/main/docs/roadmap.md).

## Install

All four options below exist for 0.1.0.

### Prebuilt binaries

The release has archives for four targets:

| Platform | Architecture | Archive |
|---|---|---|
| Linux (glibc 2.35 or newer) | x86_64 | `vowp-0.1.0-x86_64-unknown-linux-gnu.tar.gz` |
| Linux (glibc 2.35 or newer) | arm64 | `vowp-0.1.0-aarch64-unknown-linux-gnu.tar.gz` |
| macOS | Intel | `vowp-0.1.0-x86_64-apple-darwin.tar.gz` |
| macOS | Apple silicon | `vowp-0.1.0-aarch64-apple-darwin.tar.gz` |

Each archive contains `vowp`, `LICENSE`, `README.md` and
`THIRD-PARTY-LICENSES.md`. Download the archive for your machine, its `.sha256`
file, and the combined `SHA256SUMS` from the release assets:

```sh
VERSION=0.1.0
TARGET=x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, x86_64-apple-darwin, aarch64-apple-darwin
BASE=https://github.com/syver777/vowp/releases/download/v$VERSION

curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz"
curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz.sha256"
curl -fLO "$BASE/SHA256SUMS"

sha256sum -c "vowp-$VERSION-$TARGET.tar.gz.sha256"   # macOS: shasum -a 256 -c ...
tar -xzf "vowp-$VERSION-$TARGET.tar.gz"
"./vowp-$VERSION-$TARGET/vowp" --version              # must print: vowp 0.1.0
```

The Linux archives are built on Ubuntu 22.04 against glibc 2.35; musl systems
such as Alpine are not supported. The macOS archives are not code-signed or
notarized, so Gatekeeper may ask you to confirm the first run.

From a checkout, `scripts/install.sh` performs the same download, verifies the
`.sha256`, checks the binary's version and installs to `~/.local/bin` (or
`--prefix DIR`) without `sudo`:

```sh
VOWP_VERSION=0.1.0 ./scripts/install.sh --no-service --no-cron
```

### crates.io

The seven crates are published in dependency order. The binary package is
`vowp-cli`; the executable is `vowp`:

```sh
cargo install vowp-cli --version 0.1.0 --locked
vowp --version        # vowp 0.1.0
```

This builds from source and needs Rust 1.85 or newer plus a C compiler/linker
for the bundled SQLite build.

### npm

The npm package downloads the prebuilt binary for the current platform; Rust is
not required:

```sh
npm install -g vowp
vowp --version        # vowp 0.1.0
```

Requires Node.js 18 or newer. Supported platforms are the same four targets as
the prebuilt archives. Windows is not supported and is rejected by the package's
`os` field; musl/Alpine is rejected by the postinstall step with an error that
suggests building from source. Set `VOWP_SKIP_DOWNLOAD=1` to install without
the binary, or `VOWP_RELEASE_BASE_URL` to use a mirror.

### Build from source

```sh
git clone https://github.com/syver777/vowp.git
cd vowp
cargo build --release --locked --workspace
cargo install --path . --locked
vowp --version        # vowp 0.1.0
```

Prerequisites are the Rust stable toolchain selected by
[`rust-toolchain.toml`](https://github.com/syver777/vowp/blob/main/rust-toolchain.toml),
`git`, `tmux`, a C compiler/linker for the bundled SQLite build, and a harness
such as Claude Code or opencode installed and signed in. The
[install guide](https://github.com/syver777/vowp/blob/main/docs/guides/install.md)
covers the details.

## What is in 0.1.0

- Seven Rust crates: `vowp-protocol`, `vowp-store`, `vowp-graph`, `vowp-tmux`,
  `vowp-adapters`, `vowp-core` and `vowp-cli` (the `vowp` binary).
- Project and node commands (`init`, `doctor`, `up`, `down`, `status`, `board`,
  `attach`, `plan`, `node`), the job graph (`job`, `graph`), sessions
  (`session`, including `switch`, capsules and export/import), operations
  (`inbox`, `cost`, `loops`, `schedule`, `reindex`, `backup`, `schema`,
  `version`) and Work → Production (`promote`, `rollback`, `releases`). The
  full tree is in
  [`docs/reference/cli.md`](https://github.com/syver777/vowp/blob/main/docs/reference/cli.md).
- Adapters for Claude Code, opencode and a TOML-mapped generic CLI.
- Supervisor loops L1–L9: the 60-second tick and single-writer merge queue,
  worker, independent verify with a bounded fix loop, planner, keeper,
  automatic limit failover/probe-back, inbox answers, watchdog and schedules.
- Append-only session logs, handoff capsules and `session switch` between
  harness, model or node with a bounded drain and crash recovery.
- Guarded promotion: serving snapshot, candidate/serving diff, human approval by
  default, deploy, probe and a recorded rollback command.
- `scripts/install.sh` and `uninstall.sh`, a systemd user unit and a cron
  watchdog.
- The framework templates and four role skills installed by `vowp init`, the
  documentation set under `docs/`, and the runnable
  [`examples/hello-vowp`](https://github.com/syver777/vowp/blob/main/examples/hello-vowp/README.md)
  fake-adapter demo.

The complete feature list is in
[`CHANGELOG.md`](https://github.com/syver777/vowp/blob/main/CHANGELOG.md).

## What is not in 0.1.0

- No HTTP/SSE API, web or PWA window, or hosted service. VOWP opens no listening
  socket; commands use the local SQLite database or SSH.
- No ACP adapter and no cross-node live sync. Sessions move as exported bundles
  or through a cross-node switch.
- No teams, quotas, VPS metrics, parallel fan-out policies or hosted relay. The
  supported shape is one operator and one home node per project.
- No IANA time zones, phone notifications, shell completions, native GUI or
  Windows support. Schedules use UTC or a fixed offset.
- No published Homebrew tap. The formula template is in
  [`packaging/homebrew`](https://github.com/syver777/vowp/blob/main/packaging/homebrew/README.md)
  and is not filled or pushed by this release.
- No product website. GitHub, the README and `docs/` are the home.

See
[`docs/roadmap.md`](https://github.com/syver777/vowp/blob/main/docs/roadmap.md)
for the v0.2 and v0.3 direction.

## Known limitations

These are the limitations that matter for a first user. They are taken from the
current code and the test suite.

### Supervisor and tmux

| Behaviour | Workaround |
|---|---|
| `vowp up --home <dir>` creates the tmux windows without passing the home directory, so the windows can use the default `~/.vowp` home or exit. | Run with the default `~/.vowp` home, or export `VOWP_HOME=<dir>` before `vowp up`. |
| The `planner` and `keeper` windows exit when there is no session to tail, and the `inbox` window exits after one frame; only `board` and `supervisor` stay open. | Use `vowp inbox`, `vowp session tail` and `vowp board` from a terminal. |
| If the supervisor is killed between recording a job as dispatched and opening its run record, the job can stay `running` with no open run; startup reconciliation does not repair that case. | Use `vowp job retry` or `vowp job park` on the stuck job. |
| `vowp job add --brief` writes the brief in the main checkout, while a new job worktree receives the generic fallback because `.vowp/` is not copied into the worktree. | Put the brief in the job worktree before dispatch, or let the planner write it there. |
| After a deliberate `vowp down`, `vowp status --check` exits 1 and the cron watchdog or systemd unit can start the supervisor again. | Stop the watchdog and the systemd unit as well, or leave the supervisor running. |
| `vowp up --no-tmux` skips the initial layout, but supervisor startup can still create the layout on the project's tmux socket. | Use a private `TMUX_TMPDIR`; never point VOWP at your default tmux server. |
| When startup recreates the window layout, it runs the bare command `vowp` rather than the current executable, so recreation fails when `vowp` is not on `PATH`. | Install `vowp` on `PATH`, or start it from an installed location. |

The shipped end-to-end example passes with fake adapters. These supervisor paths
have less coverage in the test suite.

### Other gaps

- **L4–L8 have scripted-adapter coverage, not real-harness coverage.** The
  planner, keeper, failover, inbox and watchdog drills pass against fake
  adapters; a full real-harness planner/keeper/failover run is still future
  work. The keeper digest is a bounded view: it summarises the last 60 indexed
  events of a stalled job's session, not the full pretty log.
- **Remote-node probe on switch is skipped.** `session switch` to another node
  does not run `vowp --node <n> doctor --json`; only the local adapter registry
  is probed.
- `session watch --once` imports Claude Code transcripts; the CLI importer is
  shipped and documented. Continuous `--follow` is not available in this build,
  and the optional `vowp_adapters::claude_code::import_transcript` adapter API
  is not shipped.
- The first turn after a `session switch` passes no caller-chosen native session
  id; a fresh session gets a generated uuid-v4.
- Interval schedules align to the Unix epoch, not their creation time. Time
  zones are UTC or a fixed offset only.
- `[env.*]` has no `build` key. The promotion build guard runs
  `[merge].check_cmds`, else `[project].check_cmds`, and passes with a recorded
  note if neither is set.
- `vowp doctor` warns about missing provider API-key variables even when Claude
  Code uses its own login.
- **Platform coverage.** The test suite is exercised locally on Linux x86_64.
  The macOS and aarch64 release targets are built and smoke-tested by the
  release workflow on GitHub-hosted runners, and the macOS archives are not
  code-signed or notarized.

## Verification

The release is checked with:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
cargo check --workspace --locked
bash docs/tests/run.sh
bash scripts/tests/run.sh
scripts/release/check-packages.sh
```

The test suite is hermetic: temporary homes and repositories, private tmux
sockets and `TMUX_TMPDIR`s, fake harnesses, and no network. The shipped
end-to-end example,
[`examples/hello-vowp`](https://github.com/syver777/vowp/blob/main/examples/hello-vowp/README.md),
runs a three-job graph against fake adapters and passes.
