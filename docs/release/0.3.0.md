# VOWP 0.3.0

**Third public release — a loopback API, a browser window and session pull. Early release.**

VOWP is a VPS framework for AI agents to work on projects. v0.3 keeps the v0.2 shape — one **home**
on a Linux VPS that owns the global database, the project databases, every session log and the
supervisor, with many **surfaces** that talk to it — and adds the first browser-facing surface: a
loopback HTTP/SSE API served by `vowp-daemon`, a small web/PWA window, and a phone-friendly board
reached through the same SSH tunnel. It also adds the ACP adapter and a complete session-pull path
between nodes, including same-id and full-directory copies and a divergence report instead of a
silent merge.

VOWP does not fork or spoof a harness. It uses the official headless/JSON interfaces,
stores no harness credentials, and never reads a harness login. It is MIT licensed.

> **Status.** 0.3.0 is an early release. The v0.3 command surface and the loopback API
> are implemented and tested as described below, but the interfaces may still change.
> Read [Known limitations](#known-limitations) before using the daemon or the browser
> window for unattended or production-critical work. The features deliberately left out
> of v0.3 are in
> [`docs/roadmap.md`](https://github.com/syver777/vowp/blob/main/docs/roadmap.md).

## Install

### Prebuilt binaries

The release has archives for four targets:

| Platform | Architecture | Archive |
|---|---|---|
| Linux (glibc 2.35 or newer) | x86_64 | `vowp-0.3.0-x86_64-unknown-linux-gnu.tar.gz` |
| Linux (glibc 2.35 or newer) | arm64 | `vowp-0.3.0-aarch64-unknown-linux-gnu.tar.gz` |
| macOS | Intel | `vowp-0.3.0-x86_64-apple-darwin.tar.gz` |
| macOS | Apple silicon | `vowp-0.3.0-aarch64-apple-darwin.tar.gz` |

Each archive contains `vowp`, `LICENSE`, `README.md` and
`THIRD-PARTY-LICENSES.md`. Download the archive for your machine, its `.sha256`
file, and the combined `SHA256SUMS` from the release assets:

```sh
VERSION=0.3.0
TARGET=x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, x86_64-apple-darwin, aarch64-apple-darwin
BASE=https://github.com/syver777/vowp/releases/download/v$VERSION

curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz"
curl -fLO "$BASE/vowp-$VERSION-$TARGET.tar.gz.sha256"
curl -fLO "$BASE/SHA256SUMS"

sha256sum -c "vowp-$VERSION-$TARGET.tar.gz.sha256"   # macOS: shasum -a 256 -c ...
tar -xzf "vowp-$VERSION-$TARGET.tar.gz"
"./vowp-$VERSION-$TARGET/vowp" --version              # must print: vowp 0.3.0
```

The Linux archives are built on Ubuntu 22.04 against glibc 2.35; musl systems
such as Alpine are not supported. The macOS archives are not code-signed or
notarized, so Gatekeeper may ask you to confirm the first run.

From a checkout, `scripts/install.sh` performs the same download, verifies the
`.sha256`, checks the binary's version and installs to `~/.local/bin` (or
`--prefix DIR`) without `sudo`:

```sh
VOWP_VERSION=0.3.0 ./scripts/install.sh --no-service --no-cron
```

### The daemon and the web window

The browser window is served by the separate `vowp-daemon` binary. The archives above
contain `vowp` only; install the matching daemon as well when you want the window:

```sh
cargo install vowp-daemon --version 0.3.0 --locked
vowp-daemon --help
```

`vowp up` looks for `vowp-daemon` next to the running `vowp` executable, then on
`PATH`; `VOWP_DAEMON_BIN` overrides the lookup. A missing daemon is not fatal: the
supervisor prints a warning and keeps running without the window.

The daemon binds `127.0.0.1` on the home. Reach it from a laptop or phone through the
existing managed SSH tunnel, which `vowp up` prints for the port it actually chose:

```text
web window: http://127.0.0.1:54321/
remote window: vowp tunnel open window --remote-port 54321
  local URL: http://127.0.0.1:<local-port>/ (the command prints the chosen port)
```

### crates.io

The eight crates are published in dependency order. The binary packages are `vowp-cli`
(the `vowp` executable) and `vowp-daemon` (the loopback API):

```sh
cargo install vowp-cli --version 0.3.0 --locked
cargo install vowp-daemon --version 0.3.0 --locked
vowp --version        # vowp 0.3.0
```

This builds from source and needs Rust 1.85 or newer plus a C compiler/linker
for the bundled SQLite build.

### npm

The npm package downloads the prebuilt `vowp` binary for the current platform; Rust is
not required:

```sh
npm install -g vowp
vowp --version        # vowp 0.3.0
```

Requires Node.js 18 or newer. Supported platforms are the same four targets as
the prebuilt archives. Windows is not supported and is rejected by the package's
`os` field; musl/Alpine is rejected by the postinstall step with an error that
suggests building from source. Set `VOWP_SKIP_DOWNLOAD=1` to install without
the binary, or `VOWP_RELEASE_BASE_URL` to use a mirror. The npm package installs
`vowp` only; install `vowp-daemon` separately for the web window.

### Build from source

```sh
git clone https://github.com/syver777/vowp.git
cd vowp
cargo build --release --locked --workspace
cargo install --path . --locked
cargo install --path crates/vowp-daemon --locked
vowp --version        # vowp 0.3.0
```

Prerequisites are the Rust stable toolchain selected by
[`rust-toolchain.toml`](https://github.com/syver777/vowp/blob/main/rust-toolchain.toml),
`git`, `tmux`, a C compiler/linker for the bundled SQLite build, and a harness
such as Claude Code or opencode installed and signed in. The
[install guide](https://github.com/syver777/vowp/blob/main/docs/guides/install.md)
covers the details.

## Upgrade from 0.2.0

0.3.0 adds no store migration. The global database stays at schema 2 and each project
database stays at schema 1, so an existing v0.2 home is opened in place. Session logs,
capsules, jobs, leases and backups keep their format.

1. **Stop the supervisor and take a backup.**

   ```sh
   vowp down                                  # or: systemctl --user stop vowp
   vowp backup                                # under ~/.vowp/backups/
   cp -a ~/.vowp ~/vowp-backup-0.2.0          # a filesystem copy is the belt-and-braces copy
   ```

2. **Install the 0.3.0 binary and daemon** over the old ones (prebuilt archive,
   `scripts/install.sh`, `cargo install`, or npm for `vowp` and
   `cargo install vowp-daemon` for the window).

3. **Check the home, then start it.**

   ```sh
   vowp doctor
   vowp up
   vowp status
   vowp fleet status
   ```

   `vowp up` starts the daemon when it finds it, prints the window URL and tunnel hint,
   and keeps the supervisor running if the daemon is missing. `up --once` starts no
   daemon.

4. **Enable writes only if you want them.** Reads need no token. To enable the inbox
   answer and session switch writes, set `VOWP_API_TOKEN` in the environment that runs
   `vowp up` (for example a mode-0600 `EnvironmentFile=` on the systemd user unit),
   restart the supervisor, and enter the same value in a page's unlock panel. Without
   the variable the daemon serves reads and answers `503` for both writes.

5. **Open the window through a tunnel.** On the home, use the printed loopback URL. From
   a laptop or phone, configure the home once as a control machine
   (`vowp control init --name home <home-ssh-target>`), run the printed
   `vowp tunnel open window --remote-port <port>`, and open the local loopback URL it
   prints. Do not expose the daemon port on a public interface.

6. **Take a fresh backup outside the home.**

   ```sh
   vowp backup --to /mnt/backup/
   ```

To roll back, stop the supervisor, reinstall the 0.2.0 binaries and start it again. No
database or session-log rollback is needed because 0.3.0 did not change either schema;
keep the 0.2.0 filesystem copy until you are satisfied with the upgrade.

## What is in 0.3.0

- **Loopback HTTP and SSE API.** `vowp-daemon` serves `GET /api/v1/health`, `/board`,
  `/board/stream`, `/jobs`, `/sessions`, `/sessions/{id}`,
  `/sessions/{id}/capsules/{capsuleId}`, `/sessions/{id}/events`,
  `/sessions/{id}/events/stream`, `/nodes`, `/inbox` and `/cost`. The JSON documents are
  the same objects the CLI prints, and the exported schemas cover every document the API
  serves. The per-session stream sends one `session` frame per stored event, a periodic
  `heartbeat`, and one `resync` frame after a compacted or truncated log; the board
  stream sends the exact board document when it changes plus heartbeats.
- **Two token-gated writes.** `POST /api/v1/inbox/{id}/answer` queues the same
  `answer_inbox` request as `vowp inbox answer`, and
  `POST /api/v1/sessions/{id}/switch` runs the same `SessionService` switch as
  `vowp session switch`, including the CLI guards and a five-second drain. Both require
  `Authorization: Bearer <VOWP_API_TOKEN>`; missing or empty disables them with `503`,
  and all reads stay token-free. The token is never logged, echoed or put in a URL.
- **Web/PWA window.** `vowp up` starts the daemon as a separate child, prints
  `web window: http://127.0.0.1:<port>/` and the actual-port
  `vowp tunnel open window` hint, writes the address to `<home>/web-window`, and stops
  the child on `vowp down`, SIGINT/SIGTERM or shutdown. Embedded pages cover the board,
  session list, session detail with a live event timeline, the capsule view, cost,
  inbox and nodes. The board and session timeline use SSE with resume and a five-second
  polling fallback; the cost, inbox and nodes pages poll. The session page has the
  executor switcher and the inbox page has the answer form, both behind the shared token
  unlock panel.
- **Phone board.** `GET /board` serves the same PWA shell at a 360 px card layout: job
  counts with state labels, running-job cards with age and last-event age, slots,
  planner and keeper, active limits with resets, today's cost, the open-inbox badge, the
  last checkpoint and a visible last-updated time. A phone reaches it through the same
  loopback SSH tunnel; the home opens no public port.
- **PWA shell.** A manifest, an SVG icon and a hand-written service worker scoped to `/`.
  The worker caches only the static shell; `/api/` and stream requests always go to the
  network and are never served from the cache as authoritative data.
- **ACP adapter.** The `acp` harness kind and `acp:<model>` executor drive an Agent
  Client Protocol revision 1 server over JSON-RPC 2.0 on stdin/stdout. One prompt turn
  maps streamed updates to `tool.call`, `tool.result`, `file.change`, `plan`, one
  accumulated `assistant.message`, token-only `cost` with an unknown source, and
  `turn.ended`; VOWP keeps writing the session framing. A permission request becomes a
  `note` plus a non-retryable `error`, the adapter answers `cancelled`, and the turn
  ends — never a keystroke and never an automatic yes.
- **Session pull.** `vowp session pull <node> <session>` exports a bundle over the
  existing SSH transport, verifies its format, protocol version and checksum in private
  staging, and imports a child session. `--same-id` keeps the origin id when it is
  absent locally, with no parent. `--full` copies the whole `sessions/<id>/` directory
  (full log, blobs, capsules and `adapters.json`) as a `vowp-session-dir-v1` manifest,
  checks every size and sha256 in private staging, renames it into place and reindexes;
  the cap is 1 GiB.
- **Divergence report.** When `--same-id` or `--full` finds the source id already
  present locally, the pull prints both heads and exits 4 instead of overwriting,
  silently refusing or merging. The JSON form is a stable `session_divergence` conflict
  with `local`, `remote`, `node` and `source_session` fields. The pull writes nothing;
  the operator deletes or exports one side and pulls again. There is no force flag and
  no merge.
- **Session watch.** `vowp session watch` keeps a byte cursor and imports only newly
  completed lines, maps one Claude native uuid to one canonical VOWP session, and
  `--follow` polls every two seconds until Ctrl-C. `--once` makes one incremental pass;
  a non-TTY run without `--follow` does not hang.
- **Smaller additions.** `vowp graph --json` prints the job graph as
  `{"jobs":[...],"edges":[...]}`; `vowp job show --gates` lists every configured gate
  and marks an unrun gate `not run`; `[env.<name>].build` names the build guard's
  commands; promotion and rollback commands receive the secret values named by
  `[env.<name>].env_pass` in their child environment only; interval schedules keep the
  phase of their creation time instead of aligning to the Unix epoch.

The complete feature list is in
[`CHANGELOG.md`](https://github.com/syver777/vowp/blob/main/CHANGELOG.md).

## Acceptance evidence

The v0.3 work is covered by the repository test suite and the release-preparation
dry runs. The tests are hermetic: temporary homes and stores, a real `127.0.0.1:0`
listener for the daemon, private tmux sockets and `TMUX_TMPDIR`s, fake ACP servers,
fake `ssh` and fake harnesses, and no network beyond loopback.

### API and web window

- The daemon tests open a temporary home, bind a real loopback listener, and validate
  every JSON document against its exported JSON Schema. They cover the read routes,
  session detail and lineage, one-capsule reads, the nodes page, open/answered/dismissed
  inbox items, every cost grouping, and the two writes.
- The SSE tests read real chunked response bodies: the per-session stream compares exact
  `EventEnvelope` frames, appends live events and exercises the `resync` path; the board
  stream validates its `board` frames, compares them with `GET /api/v1/board` apart from
  `at`, changes a job through a writable store to receive the next snapshot, and observes
  heartbeats while the snapshot is stable.
- The write tests pin `503` without a token, `401` for a missing or wrong Bearer value
  before the body is parsed, the trimmed answer with exactly one queued request row, the
  switch guards (`404`, running without `force`, switching, closed and limited target all
  `409`), and that neither handler creates or migrates a home.
- The page tests are HTTP-only tests over the same temporary home and a real listener.
  They pin the board and session stream paths, the `after_seq` resume, the reconnect and
  polling fallback text, the capsule panel and lineage, the token unlock and
  `sessionStorage` use, the absence of a token in a URL, the cost chart's known and
  unknown rows, the nodes table, and the PWA manifest and service-worker asset types,
  scope and API/SSE bypass.
- The `vowp up` tests pin the daemon child's `--home`/`--project`/`--port` arguments,
  the inherited `VOWP_API_TOKEN`, the printed address and exact tunnel hint, the detached
  address file, the SIGTERM/`down` shutdown without an orphan, and the warning-and-continue
  path when the binary is missing.

**Not run:** a real browser session on a Mac or phone, and a real click-through of the
window over an SSH tunnel. The page tests exercise the HTTP contract, not a browser
engine. The owner-device checks in the launch checklist cover these before the release
is announced.

### ACP adapter

- The adapter tests run a fake ACP server (a local Python script, no network) through
  `initialize`, `session/new` and one `session/prompt`. They cover a clean turn and a
  refused permission, an exited-without-result server, malformed JSON, an unknown
  method, a JSON-RPC quota error, event ordering, and `stop()` killing the process group.
- `vowp doctor` probes ACP only when `[harnesses.acp]` or an ACP profile rung is
  configured; the tests cover the configured and unconfigured cases.

**Not run:** a real ACP server, native resume, a permission UI, streaming chunk events,
an inbox-approval round trip, and ACP cost receipts. These remain planned.

### Session pull and divergence

- The pull tests use a fake `ssh` harness and a temporary remote home. They cover the
  child import, corrupt and truncated bundles, a failed remote export, `--same-id` with
  a missing and a present id, duplicate event ids, `--full` with a full log, a blob, a
  capsule and `adapters.json`, corrupt and over-cap snapshots, and the store's manifest
  digest, size and path checks.
- The divergence tests cover a present local id for both the bundle and full paths:
  both heads are printed, the JSON conflict is stable, exit is 4, and the local home is
  left unchanged.
- The `session watch` tests cover the byte cursor, a partial final line, a shrunken
  transcript, one session per Claude uuid, `--once`, the `--follow` flag and a clean
  SIGINT exit.

### Release preparation

The release commit is checked with:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
cargo check --workspace --locked
bash docs/tests/run.sh
bash scripts/tests/run.sh
scripts/release/check-packages.sh
scripts/release/publish-crates.sh
```

The archives are built by `.github/workflows/release.yml` on native runners for the four
targets, with `--locked`, a `vowp --version` smoke test, the third-party licence check,
`package-archive.sh`, per-archive `.sha256` files and the combined `SHA256SUMS`. The
workflow creates a **draft** release; the orchestrator verifies every asset and publishes
it after the owner's review.

The release-preparation dry run packages four archive names and their checksums locally.
Only the native Linux x86_64 archive contains a real target binary; the other three are
produced from the native binary to exercise the packaging and checksum path. The release
workflow builds and smoke-tests each real target on its native runner before the draft is
published. **The local dry run is not a substitute for that workflow run.**

## Known limitations

These are the limits that matter for a first v0.3 user. They are taken from the current
code and the tests.

### API and daemon

- **Loopback only.** The daemon binds `127.0.0.1` and has no public listener, TLS
  termination, hosted relay or remote access without SSH. Exposing the port directly is
  not supported. A phone reaches the board through the SSH tunnel.
- **Two writes only.** Only the inbox answer and the local session switch are exposed as
  HTTP writes. Job retry/park/cancel, capsule edits, node add/remove/probe and a chat turn
  from the browser remain CLI/MCP operations. There are no placeholder routes.
- **One project per daemon.** `vowp up` passes the checkout's project or the only
  registered project; an ambiguous or empty home leaves the window off with a warning.
  Starting `vowp-daemon` directly still takes `--project`.
- **Reads are unauthenticated on loopback.** Writes need the bearer token; reads do not.
  Anyone who can reach the loopback port can read the served project's board, sessions,
  events, inbox and cost. Keep the port behind SSH and do not forward it publicly.
- **No token store or rotation service.** The daemon reads `VOWP_API_TOKEN` at startup.
  Rotating it means restarting the daemon with the new value and unlocking the pages
  again. There is no multi-user account, role or per-user audit. The inbox answer records
  `answered_by = "web"`; the switch uses the normal session ledger.
- **No store creation or migration.** Both handlers open the existing home. A missing or
  older home is refused rather than migrated. Run `vowp up` or `vowp migrate` first.
- **Stream recovery is explicit.** A session stream that falls behind a compacted,
  truncated or removed log gets one `resync` frame and closes; the page reconnects from
  the named cursor. The board stream has no cursor, resume or resync; it sends the next
  snapshot. Cost, inbox and nodes pages still poll every five seconds and have no live
  reconnect UI.

### Web window and phone board

- **The daemon is a separate binary.** The prebuilt `vowp` archives and the npm package
  install only `vowp`. Install `vowp-daemon` separately (crates.io or from source) or set
  `VOWP_DAEMON_BIN`. Without it `vowp up` warns and the window stays off; the supervisor
  is unaffected.
- **PWA caches the shell only.** The service worker bypasses `/api/` and stream
  requests entirely and caches only the static page shell. Offline data entry, offline
  event data and push notifications are out of scope. The page shells keep their error
  states offline.
- **No native app and no push.** The phone board is the same PWA at a narrow width. There
  is no iOS/Android app and no notification service; a stalled inbox item is visible the
  next time the page is opened or polled.
- **No browser chat turn.** The window can answer an inbox item and switch the local
  executor. Sending a new chat turn from the browser needs a run queue and cancellation
  and remains later work.
- **No code editor or terminal.** The pages link to the CLI and the tmux windows; they do
  not replace them.
- **Pages are hand-written shells.** There is no frontend framework or TypeScript build
  step. The tests are HTTP-only; no browser automation runs in the repository.

### ACP adapter

- **First slice only.** The adapter is tested against a fake ACP server, not a real ACP
  server. Real servers, authentication, native resume (`session/load`), a permission UI
  or live pause, streaming chunk events, an inbox-approval fallback, the process-usage
  sidecar and ACP cost receipts remain planned.
- **Permission requests end the turn.** VOWP records a `note` and a non-retryable `error`
  and answers `cancelled`. It never auto-approves and never sends keystrokes.
- **Cost is tokens only.** ACP usage is stored with `CostSource::Unknown` and no USD;
  the price table in core remains the fallback, and no price is invented by the adapter.
- **One assistant message per turn.** Chunked assistant text is accumulated and emitted
  once at turn end; per-chunk events are not implemented.

### Session pull and divergence

- **One-way snapshots.** Pull is explicit `session pull` only. There is no
  `session push`, no bidirectional `session sync`, and no automatic conflict resolution.
  The source is not modified or locked, and no live lease is migrated.
- **Divergence is a report, not a merge.** When both sides have the same id, the pull
  prints both heads and exits 4. The operator must delete or export one side and pull
  again. There is no force flag.
- **The full pull has a 1 GiB cap.** An over-cap, unreadable or corrupt source is refused
  before anything is copied. There is no partial copy, no blob placeholder and no
  configurable limit in the CLI. A compacted source has no `log.jsonl` and is refused;
  use the bundle pull for it.
- **Same build on both nodes.** The full pull uses the source's hidden
  `session dir-export`. Both nodes must run a build with that command. Leave the source
  lease released or quiescent while the snapshot runs.
- **Bundle pulls carry a tail.** The default and same-id bundle pulls copy the bundle's
  replayable tail (20 events by default, up to 500 with `--tail` on export), not the full
  log. Use `--full` when the whole directory is wanted.
- **No daemon transport.** SSH remains the only pull transport; the HTTP API is not a
  session-sync transport.

### Platform and product shape

- **One operator, one home.** There is no replication, leader election or multi-home
  scheduler, and no multi-user accounts, quotas, roles or audit beyond the existing
  ledger. A second home is a separate installation.
- **Linux home, Linux/macOS control.** Windows is not supported and there is no native
  VOWP desktop app; the apps are the surfaces. The macOS and aarch64 release targets are
  built and smoke-tested by the release workflow on native runners, not by the local
  preparation run.
- **No continuous app-transcript watcher.** The mirror runs at orchestrator
  create/resume/startup; between those calls the app owns its transcript.
- **Secret redaction still has known gaps.** The v0.2 secret-redaction limits remain:
  exact-value redaction does not cover the supervisor log, gate command evidence, ledger
  rows, the switch turn path or the `session watch` importer. Treat every harness as able
  to persist what it prints; the secret-scan gate is a backstop, not a guarantee.
- **The npm wrapper and the archives do not install the daemon.** See the daemon note
  above; the window needs a separate `vowp-daemon` install.
